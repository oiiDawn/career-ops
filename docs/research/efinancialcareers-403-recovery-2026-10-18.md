# eFinancialCareers 403 队列修复与只读验收

What this change does: 详情页 HTTP 403 只记录当前请求失败，不再清空整个来源的候选队列。继续其他职位和关键词，不重试同一个失败职位，不延长总耗时预算。

## Ponytail 审查

按单用户本机、四个共享关键词、每来源最多 50 个有效职位评估。检查了共享 `collectSearch`、真实 provider.fetch 浏览器读取、Node collect 调用方、Python 收集与发布边界、既有重试/截止时间测试及当前操作文档。

### Must fix（已修复）

1. **将单页拒绝推断为整个来源失效**（`adapters/node/providers/search.mjs:220`）
   - **What this is:** HTTP 403 表示当前请求被拒绝；共享详情错误处理负责决定是否继续其他候选。
   - **Problem:** 原代码收到一个 403 就清空所有关键词队列。回归用三个不同职位复现：第一项返回 403 后，同关键词剩余项和另一关键词都未执行。
   - **Fix:** 从共用的来源停止条件中移除 403，复用原有失败记录、去重和队列推进。生产代码只改一行，不加站点例外、重试、计数器、配置或恢复框架。
   - **If we skip it:** 一次局部拒绝仍会无依据地丢弃全部未尝试职位。

该规则适用于所有 search 来源，而不是只给 eFinancialCareers 加例外。LinkedIn 详情 403 也会跳过当前职位继续，但不重试；LinkedIn 的 429 退避未改变。本轮没有额外运行 LinkedIn 实验。HTTP401/405 及 Web 来源 HTTP429 的原有停止行为保留；搜索请求失败仍只结束对应关键词。

## 回归与预算

- 修改前运行 `node tests/adapters/providers/search.test.mjs`，回归失败：只读取第一个 403 职位，没有继续另两个职位。
- 修改后回归通过：按轮转顺序继续另一关键词及同关键词剩余职位，取得两个完整 JD；其他关键词重复返回的失败职位不会再次读取。最终仍标记 incomplete_details 并保留 403 警告。
- 另一个回归在首个 403 时推进模拟时钟超过固定来源截止时间，确认不开始后续请求。正常 600 秒 provider 预算、525 秒采集窗口和 75 秒预留未改。
- 既有 LinkedIn 重试、来源范围、完整 JD 与身份校验回归通过。
- `node scripts/check-syntax.mjs`：240 个 `.mjs` 通过。
- `.venv/bin/python -B tests/business/workflow-scan-test.py` 通过。
